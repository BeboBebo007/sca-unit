# قالب الخدمة الآمنة القابلة لإعادة الاستخدام
## Secure Reusable Python Service Template

**الإصدار:** 1.0  
**الحالة:** قالب تأسيسي قيد الاستخراج والتعميم  
**الفرع:** `template/secure-python-service-v1`  
**اللغة الأساسية:** Python  
**نمط الاتصال:** HTTP / JSON  
**نطاق التشغيل الحالي:** خدمة محلية آمنة قابلة للتطوير لاحقًا إلى خدمة شبكية أو سحابية

---

# 1. التعريف

هذا القالب هو أساس برمجي عام لإنشاء خدمات Python آمنة تستقبل بيانات منظمة عبر HTTP، وتتحقق من صحتها، وتشغّل منطق معالجة قابلًا للاستبدال، ثم تعيد نتيجة موحدة وتسجل الحدث في سجل تدقيق.

الهدف منه هو منع إعادة بناء المكونات الأساسية في كل مكتبة أو منتج جديد، بحيث يمكن إعادة استخدام طبقات التشغيل والحماية والتحقق والاختبار، مع استبدال منطق المنتج فقط.

القالب ليس منتجًا نهائيًا مستقلًا، بل قاعدة هندسية يمكن البناء عليها لإنشاء خدمات تحليل، ومحركات معالجة، وأدوات داخلية، وخدمات مصغرة، وواجهات خلفية للويب والهاتف.

---

# 2. المشكلة التي يحلها القالب

عند إنشاء مكتبة أو منتج جديد تتكرر الحاجة إلى بناء العناصر نفسها:

- خادم HTTP.
- استقبال JSON.
- التحقق من المدخلات.
- حماية الخدمة بمفتاح.
- تحديد حجم الطلبات.
- معالجة الأخطاء.
- نقطة فحص الصحة.
- سجل التدقيق.
- اختبارات آلية.
- إدارة متغيرات البيئة.
- توحيد شكل الاستجابات.
- حفظ الأدلة التشغيلية.

هذا التكرار يستهلك الوقت ويزيد احتمالات الأخطاء. لذلك يفصل القالب بين البنية التشغيلية العامة القابلة لإعادة الاستخدام، ومنطق المنتج أو المكتبة الخاص الذي يجب استبداله.

---

# 3. الهدف الاستراتيجي

الهدف هو إنشاء قاعدة موحدة يمكن استخدامها في مشاريع متعددة دون البدء من الصفر.

عند إنشاء منتج جديد يحتاج المطور أساسًا إلى:

1. تغيير اسم الخدمة والحزمة.
2. تعريف نموذج البيانات المطلوب.
3. استبدال دالة المعالجة الأساسية.
4. تعديل اختبارات المنتج.
5. تحديث الوثائق والتعريفات.
6. إنشاء مفتاح وملف بيئة خاصين بالمشروع.

أما طبقات HTTP والحماية والحدود والتسجيل والاختبارات الأساسية فتبقى قابلة لإعادة الاستخدام.

---

# 4. الحدود الحالية للقالب

النسخة الحالية مستخرجة من نموذج أولي لخدمة محلية، ولذلك قد تحتوي مؤقتًا على أسماء أو مراجع مرتبطة بالمشروع المصدر.

قبل اعتماد القالب كنسخة عامة نهائية يجب إزالة أو استبدال:

- اسم `SCA-Unit`.
- أسماء الحزم الخاصة بالمشروع المصدر.
- منطق التقييم الخاص.
- نماذج البيانات الخاصة.
- رسائل الخدمة الخاصة.
- أسماء ملفات الأدلة المرتبطة بالمشروع.
- أي أمثلة تحمل هوية المنتج المصدر.
- أي آليات محمية أو مملوكة لا يراد تعميمها.

لا يجوز اعتبار هذه النسخة عامة نهائية قبل إكمال عملية التنظيف والتعميم والتحقق.

---

# 5. المعمارية العامة

## 5.1 طبقة التشغيل

مسؤولة عن تشغيل الخدمة، وتحديد المضيف والمنفذ، وتحميل إعدادات البيئة، وبدء خادم HTTP، وإيقاف الخدمة بصورة سليمة.

## 5.2 طبقة واجهة HTTP

مسؤولة عن استقبال طلبات `GET` و`POST`، وتوجيهها، والتحقق من نوع المحتوى، وقراءة جسم الطلب، وتطبيق حد الحجم، وفك JSON، وإعادة رموز HTTP الصحيحة.

## 5.3 طبقة المصادقة

تعتمد النسخة الحالية على مفتاح خدمة يرسل في الرأس:

```text
X-API-Key
```

ويتمت مقارنة المفتاح المرسل بالمفتاح الموجود في متغير البيئة:

```text
SCA_UNIT_API_KEY
```

عند تعميم القالب يجب تغيير اسم المتغير إلى اسم عام مثل:

```text
SERVICE_API_KEY
```

## 5.4 طبقة التحقق من المدخلات

مسؤولة عن التأكد من أن جسم الطلب كائن JSON، ووجود الحقول المطلوبة، ورفض الأنواع غير الصحيحة والطلبات الناقصة، وتمرير بيانات صالحة فقط إلى منطق المعالجة.

## 5.5 طبقة منطق المنتج

هذه هي الطبقة التي تستبدل عند إنشاء منتج جديد. يجب أن تستقبل البيانات التي اجتازت التحقق، وتنفذ الخوارزمية أو التحليل الخاص، وتنتج تقريرًا موحدًا، وتبقى مستقلة عن تفاصيل HTTP.

## 5.6 طبقة سجل التدقيق

تسجل معلومات تشغيلية مثل معرف الطلب، والتوقيت العالمي، وهوية العملية، وحالة التنفيذ. يجب ألا تحتوي السجلات على مفاتيح API أو كلمات مرور أو أسرار أو بيانات شخصية غير ضرورية أو تفاصيل داخلية محمية.

## 5.7 طبقة الاختبارات

يجب أن تغطي الاختبارات الطلب الصحيح، والطلب الناقص، وJSON التالف، ونوع المحتوى غير الصحيح، والمفتاح الخاطئ، وغياب المفتاح، وتجاوز حد الحجم، ونقطة فحص الصحة، وسجل التدقيق، ومنطق المنتج.

# 6. نقاط النهاية الأساسية

## 6.1 فحص الصحة

```http
GET /health
```

مثال استجابة:

```json
{
  "status": "ok",
  "service": "Secure Python Service",
  "version": "1.0",
  "input_mode": "direct-json-payload"
}
```

## 6.2 تنفيذ المعالجة

```http
POST /assess
```

اسم المسار الحالي مرتبط بالمشروع المصدر. عند تعميم القالب يمكن تغييره إلى `POST /process` أو إلى مسار خاص بالمنتج.

# 7. الحماية الحالية

تشمل الحماية المثبتة في النسخة الحالية:

- مفتاح API.
- رفض المفتاح الخاطئ بالحالة `401`.
- رفض الخدمة غير المهيأة بالحالة `503`.
- رفض JSON التالف بالحالة `400`.
- رفض الطلب الناقص بالحالة `400`.
- رفض نوع المحتوى غير الصحيح بالحالة `415`.
- رفض الطلبات المتجاوزة للحد بالحالة `413`.
- عدم إعادة تفاصيل الاستثناءات الداخلية للمستخدم.
- تحديد حد أعلى لجسم الطلب.
- تشغيل محلي افتراضيًا على `127.0.0.1`.
- حفظ الأسرار في ملف بيئة مستبعد من Git.

هذه الحماية مناسبة لنموذج أولي محلي، لكنها ليست وحدها كافية للنشر العام على الإنترنت.

# 8. متطلبات النشر العام مستقبلًا

قبل نشر أي منتج مشتق من القالب للعامة يجب إضافة أو تقييم HTTPS، وخادم إنتاج مناسب، وReverse Proxy، وتدوير المفاتيح، وتحديد معدل الطلبات، والسجلات الأمنية المركزية، والمراقبة، والمهلات، وحدود الموارد، وإدارة الأسرار الاحترافية، واختبارات الاختراق، وسياسات الاحتفاظ بالسجلات، وحماية البيانات الشخصية، والنسخ الاحتياطية، وعزل بيئة التنفيذ.

# 9. طريقة إنشاء منتج جديد من القالب

1. نسخ القالب إلى مستودع أو مجلد جديد.
2. تغيير اسم المشروع والحزمة والخدمة.
3. تعريف نموذج الإدخال وقواعد التحقق.
4. استبدال منطق المعالجة بمنطق المنتج.

7. تشغيل جميع الاختبارات قبل إنشاء أي إصدار.

---

# 10. ما يجب أن يبقى عامًا

يمكن الاحتفاظ بتشغيل الخادم، ومعالجة HTTP، وفحص الصحة، والتحقق من نوع المحتوى، وتحديد حجم الطلب، والمصادقة الأساسية، وتحويل JSON، والاستجابات الموحدة، وسجل التدقيق العام، وبنية الاختبارات، وتحميل البيئة، وتعليمات التشغيل، وآلية حفظ الأدلة.

---

# 11. ما يجب ألا يدخل القالب العام

يجب عدم تضمين الخوارزميات المملوكة، وآليات SCA المحمية، وآليات AMNE المحمية، والأسرار، والمفاتيح الحقيقية، وملفات البيئة المحلية، وبيانات العملاء، والسجلات الحساسة، ومطالبات البراءات غير المنشورة، والتفاصيل التنفيذية التي تكشف آلية مملوكة.

---

# 12. سياسة الملكية الفكرية

هذا القالب يمثل طبقة تشغيلية عامة، ولا يعني نشره أو نسخه التخلي عن أي حقوق مرتبطة بالخوارزميات أو المنتجات التي تستخدمه.

يجب التمييز دائمًا بين البنية العامة، مثل HTTP وJSON والتحقق والمصادقة والتدقيق، وبين الابتكار الخاص، مثل الخوارزمية وقواعد القرار وآليات القياس والنماذج البنيوية.

قبل إصدار نسخة عامة يجب إجراء مراجعة مستقلة للتأكد من عدم تسرب أي جزء مملوك.

---

# 13. سياسة الأسرار

1. لا تحفظ المفاتيح داخل الشيفرة.
2. لا ترفع `.env.local` إلى Git.
3. لا تستخدم مفتاحًا حقيقيًا في الاختبارات العامة.
4. استخدم مفاتيح تجريبية منفصلة.
5. غيّر المفتاح عند الاشتباه بتسربه.
6. لا تعرض المفتاح في السجلات.
7. لا تحفظ المفتاح داخل ملفات الأدلة.
8. استخدم مدير أسرار عند النشر الإنتاجي.

---

# 14. سياسة الأدلة التشغيلية

يمكن حفظ نتائج الاختبارات، ورموز الاستجابة، ونجاح فحص الصحة، ومعرفات الطلبات التجريبية، وحالة اكتمال التشغيل. يجب أن تكون الأدلة قابلة لإعادة التحقق، وخالية من الأسرار، ومرتبطة بمرحلة واضحة، وقابلة للربط بالتزام معين.

---

# 15. سياسة الإصدارات والعلامات

يقترح استخدام `template-v1.0.0` للنسخة العامة الأولى، و`template-v1.1.0` لإضافة خصائص متوافقة، و`template-v2.0.0` للتغييرات غير المتوافقة.

لا تنشأ علامة إصدار نهائي قبل نجاح الاختبارات، وتنظيف أسماء المشروع المصدر، ومراجعة الأسرار والملكية الفكرية، وتجربة إنشاء منتج مشتق واحد على الأقل.

---

# 16. معايير اكتمال القالب العام

يعتبر القالب جاهزًا للإصدار الأول عندما:

- لا توجد أسماء خاصة بالمشروع المصدر.
- لا يوجد منطق خوارزمي خاص.
- لا توجد أسرار.
- جميع الاختبارات ناجحة.
- يوجد ملف مثال للبيئة دون مفتاح حقيقي.
- توجد وثيقة تشغيل ووثيقة تخصيص.
- توجد سياسة استخدام واضحة.
- يمكن إنشاء خدمة جديدة دون تعديل طبقة الحماية.
- تم اختبار نسخة مشتقة واحدة على الأقل.
- تم إنشاء ملف مضغوط ثابت.
- تم إنشاء علامة Git ثابتة.

---

# 17. الوضع الحالي

تم إثبات العناصر التالية في المشروع المصدر قبل بدء الاستخراج:

- نجاح الطلب المباشر عبر HTTP.
- نجاح سجل التدقيق.
- رفض المفتاح الخاطئ بالحالة `401`.
- رفض الطلب الناقص بالحالة `400`.
- رفض JSON التالف بالحالة `400`.
- رفض نوع المحتوى غير الصحيح بالحالة `415`.
- رفض الطلب الكبير بالحالة `413`.
- نجاح نقطة الصحة.
- نجاح 24 اختبارًا آليًا.
- تشغيل الخدمة من ملف بيئة محلي مستبعد من Git.

هذه النتائج تمثل أساسًا مثبتًا لاستخراج القالب، لكنها لا تعني أن عملية التعميم اكتملت بعد.

4. توحيد أسماء متغيرات البيئة.

# 19. الخلاصة

هذا القالب أصل هندسي قابل لإعادة الاستخدام، هدفه اختصار الطريق بين الفكرة والمنتج العامل.

قيمته الأساسية ليست في خوارزمية بعينها، بل في توفير طبقة موحدة ومختبرة تشمل التشغيل، والحماية، والتحقق، والاتصال، والأخطاء، والتدقيق، والاختبارات، والتوثيق.

عند اكتمال تعميمه يمكن استخدامه كأساس لعدة مكتبات ومنتجات، مع الحفاظ على الفصل الصارم بين البنية التشغيلية العامة والابتكارات الخاصة بكل مشروع.
